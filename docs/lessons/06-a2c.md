# 06 · A2C: a critic, bootstrapping and the truncation fix

REINFORCE (lesson 05) works in principle and struggles in practice: one gradient step per
tens of thousands of decisions, weights that are mostly noise, and a deterministic driver that
was never what training optimized. A2C ("advantage actor-critic") keeps the same policy and
the same policy-gradient idea, and adds a second network, the *critic*, that predicts how much
return to expect from a state. That one addition pays three times: it cuts the gradient's
variance, it lets the algorithm learn from short pieces of episodes instead of whole ones, and it
fixes REINFORCE's truncation bias.

Files: [`racer/algos/a2c.py`](../../racer/algos/a2c.py), [`racer/nets_torch.py`](../../racer/nets_torch.py),
[`configs/a2c.toml`](../../configs/a2c.toml), [`configs/budgets.md`](../../configs/budgets.md),
[`tests/test_a2c.py`](../../tests/test_a2c.py).

## Baselines: subtracting a number changes nothing on average

Lesson 05's estimate weighted each step's score by its reward-to-go:
`∇J ≈ E[Σ_t ∇log π_θ(a_t|s_t) · G_t]`. Early in training every `G_t` was negative, so every
sampled action was pushed down, the good ones a little less than the bad ones. The useful
information is only in the *differences* between returns; the common offset is pure noise that
the batch has to average away.

So subtract something. Let `b(s_t)` be any function of the state (not of the action). Then

```
E[ ∇log π_θ(a_t | s_t) · b(s_t) ] = 0
```

Proof: condition on the history up to `s_t`. Then `b(s_t)` is a fixed number and only
`a_t ~ π_θ(·|s_t)` is random:

```
E_{a ~ π_θ(·|s_t)} [ ∇log π_θ(a | s_t) · b(s_t) ] = b(s_t) · ∫ π_θ(a|s_t) ∇log π_θ(a|s_t) da
                                                 = b(s_t) · ∫ ∇π_θ(a|s_t) da
                                                 = b(s_t) · ∇ ∫ π_θ(a|s_t) da  =  b(s_t) · ∇1  =  0
```

It is the same three lines that justified reward-to-go in lesson 05 (there the fixed number was
a past reward). Taking the expectation over histories as well keeps it zero. So

```
∇J = E[ Σ_t ∇log π_θ(a_t | s_t) · (G_t - b(s_t)) ]
```

for *any* `b` that does not look at `a_t`: the expectation, the direction we step in on average,
is unchanged. What changes is the variance. The estimate is a sum of terms
`score · (G - b)`; when `G - b` is small on average, so are the fluctuations. A good choice is
the expected return from `s_t` under the current policy, the *state value*

```
V^π(s) = E[ G_t | s_t = s ]
```

Then `G_t - V(s_t)`, the *advantage*, says how much better this particular continuation went
than what was expected from this state. Positive: make that action more likely; negative: less.
An action in a hopeless state (the car about to hit the wall whatever it does) no longer gets a
big negative push just for being there; only the difference between its outcome and the usual
outcome from that state counts. (The value baseline is not exactly the variance-minimizing one,
which would weight by the squared score, but it is close and it is what everyone uses.)

The catch: nobody gives us `V^π`. We learn an approximation `V_φ(s)`, a second network with its
own parameters `φ`. Because `V_φ` depends only on the state, using it as `b` still adds no bias,
however wrong it is. Bias enters only with the next step, bootstrapping.

## The critic

[`Critic`](../../racer/nets_torch.py#L51-L59) is the same 12-64-64 tanh MLP as the actor's body
with one output: `V_φ(s)`. It is trained by regression: for every state in the batch we have a
target return `R_t`, and the critic minimizes the squared error

```
L_V(φ) = mean over the batch of (V_φ(s_t) - R_t)²
```

Minimizing a squared error makes `V_φ(s)` an estimate of the *conditional mean* of `R` given `s`,
which is what a value is. The actor and critic are separate networks
([a2c.py#L158-L161](../../racer/algos/a2c.py#L158-L161)) trained by one Adam optimizer on the sum
of both losses:

```python
advantage = returns - values
policy_loss = -(logp * advantage.detach()).mean()
value_loss = (values - returns).pow(2).mean()
return policy_loss + value_coef * value_loss - entropy_coef * entropy.mean(), value_loss
```

([`a2c_loss`](../../racer/algos/a2c.py#L137-L147)). Two details:

- **`advantage.detach()`.** To the actor the advantage is a weight, like `G_t` in REINFORCE.
  Without the detach, the policy loss would also have a gradient with respect to `φ` through
  `values`, and minimizing `-logp · (R - V)` would push `V` *up* wherever `logp` is positive and
  down elsewhere: the actor would be training the critic to flatter it.
- **`value_coef = 0.5`.** Because both losses are added and share one optimizer and one
  gradient-norm clip (below), this sets how much of each update goes to the critic. The two
  networks have no shared weights, so without the clip the coefficient would only rescale the
  critic's gradient, and Adam largely undoes constant rescalings. *With* the clip it matters: the
  clip acts on the norm of the combined gradient. Experiment 2 changes it.

`entropy_coef = 0` in the default config, so the entropy term is off here (the entropy of a
normal is `log σ + const`, so the bonus would push `log_std` up and keep exploration alive).

## Bootstrapping: n-step returns

REINFORCE had to wait for every episode to end before it could compute a single `G_t`, which is
why its batches held whole episodes (up to 1,350 decisions each) and why it got so few updates.
With a critic there is a shortcut. Split the reward-to-go after `n` steps:

```
G_t = r_t + γ r_{t+1} + ... + γ^{n-1} r_{t+n-1}  +  γ^n G_{t+n}
```

and replace the unknown tail `G_{t+n}` by the critic's estimate of it:

```
R_t^{(n)} = r_t + γ r_{t+1} + ... + γ^{n-1} r_{t+n-1}  +  γ^n V_φ(s_{t+n})
```

This is *bootstrapping*: using the current estimate of a value to build the target for another.
Now the learner needs only `n` steps of experience, not a whole episode. A2C drives every car for
`n_steps = 32` decisions, updates, and carries on from where the cars are: no reset, episodes
simply span several rollouts ([`collect_rollout`](../../racer/algos/a2c.py#L72-L108)).
[`nstep_returns`](../../racer/algos/a2c.py#L119-L132) computes the targets with the same backward
recursion as REINFORCE, seeded with `V(s_last)` instead of 0:

```python
running = np.asarray(last_values, dtype=float)          # V of the state after the last step
for t in reversed(range(len(rewards))):
    running = rewards[t] + gamma * running * (1.0 - dones[t])
    returns[t] = running
```

So the *last* step of a rollout gets a 1-step target `r + γV(s')`, the first one a 32-step target;
every step in between gets whatever is left until the rollout's end. Where an episode ended
(`dones[t]`), the `(1 - dones[t])` cuts the chain, so nothing from the respawned car's next
episode leaks backwards ([`test_nstep_returns_done_cuts_bootstrap`](../../tests/test_a2c.py#L19-L23)).

**The bias-variance trade.** The Monte Carlo return `G_t` is an unbiased sample of the value but
carries the noise of every reward to the episode's end. `R^{(n)}` carries only `n` rewards of
noise, plus the critic's error. If the critic is wrong, the target is wrong in the same direction
every time: that is bias, and unlike the baseline it does change the expected gradient. `n` sets
the mix: `n = 1` is all critic (low variance, as biased as the critic), `n = ∞` is REINFORCE with
a baseline (no bootstrap bias, full variance). Experiment 1 tries 8 and 32.

**The update.** Each iteration uses `n_cars × n_steps = 16 × 32 = 512` decisions for one Adam
step (`lr = 7e-4`), with the gradient's total norm clipped to `max_grad_norm = 0.5`
([line 199](../../racer/algos/a2c.py#L199)): if the combined gradient of actor and critic is
longer than 0.5, it is scaled down to length 0.5. On 4.5M decisions that is 8,790 updates;
REINFORCE got between 125 and 388 (lesson 05).

## The truncation fix

Lesson 05 ended with REINFORCE's truncation bias: at the 90 s limit (or after the second lap) the
reward-to-go was cut to the rewards actually seen, as if the car had crashed. Lesson 03 explained
the distinction the simulator makes: *terminated* (a crash or wrong way: no future, value 0) and
*truncated* (time limit or max laps: the car could have gone on). With a critic the right target
for a truncated step is available:

```
target at a truncated step:   r_t + γ V_φ(s_{t+1})        s_{t+1} = where the car really was
target at a terminated step:  r_t
```

Two pieces of code do it. With auto-reset, the observation the sim returns for a finished car is
already its *respawn*, so [lines 94-97](../../racer/algos/a2c.py#L94-L97) ask the critic about
`result.final_obs` instead, the state before the reset, and record `final_values`. Then
[`add_truncation_bootstrap`](../../racer/algos/a2c.py#L113-L116) folds it into the reward:

```python
return rewards + gamma * final_values * truncated
```

After that, the step is treated as `done` like any other ending (the chain is cut), but its
reward already contains the discounted value of the future it was denied
([`test_truncation_bootstrap`](../../tests/test_a2c.py#L26-L31): reward 1, `γ = 0.9`,
`V(final_obs) = 2` gives target 2.8). A crash adds nothing.

Why it matters more here than in REINFORCE: the critic learns from these targets. Time is not in
the observation, so a car mid-straight at 90 s looks exactly like the same car at 30 s. Treat
truncation as a crash, and the critic sees the same state with target ≈ 0 on one visit and ≈ 12
on another (a steady 20 m/s, lesson 05's arithmetic); its estimate is pulled down everywhere and
the advantages of perfectly good actions near the time limit come out negative.

One thing the fix assumes: that `V(final_obs)` is a sensible value for the state the car ended
in. After `max_laps` the episode ends by design and the observation does not include the lap
count, so the critic values the finishing car like any car at that spot, as if the race went on.
That is the convention the environment chose (lesson 03: finishing is truncation, not
termination), and it is consistent: the critic never has to predict a cliff it cannot see.

## Explained variance: is the critic any good?

A critic is useful only if it predicts returns better than a constant would. The standard check,
logged every iteration ([lines 215-217](../../racer/algos/a2c.py#L215-L217)):

```
explained_variance = 1 - Var(R - V) / Var(R)
```

over the batch's targets `R` and the critic's predictions `V` (before this update). It is 1 if
the critic predicts every target exactly, 0 if it does no better than predicting the batch mean
for every state, and negative if it is worse than that. In terms of the baseline argument:
`Var(R - V)` is roughly the variance left in the advantages, so explained variance is the
fraction of the weight noise the critic removed.

## Reading the diff

[a2c.py's docstring](../../racer/algos/a2c.py#L3) says to read it as a diff against REINFORCE,
and that is the best way:

```sh
diff racer/algos/reinforce.py racer/algos/a2c.py
```

Most of the output is renames (`ReinforceConfig` → `A2CConfig`, `"reinforce"` → `"a2c"`) and the
moved `TorchPolicy` (A2C imports it, so both methods evaluate and render identically). The
hunks that carry the algorithm:

**Collection: fixed-length rollouts instead of whole episodes.**

```diff
<     obs = sim.reset()
<     ...
<     while len(episodes) < n_episodes:
---
>     buf = {k: [] for k in ("obs", "actions", "rewards", "terminated", "truncated", "final_values")}
>     for _ in range(n_steps):
```

No reset, no per-car episode lists, no dropped half-episodes: every car drives exactly `n_steps`
decisions and the batch is a `(T, N)` grid. The `obs = sim.reset()` moved into `train_a2c`
and runs once ([line 167](../../racer/algos/a2c.py#L167)). This also removes REINFORCE's
short-episode bias (lesson 05): every decision driven is used, whatever kind of episode it
belongs to.

**Returns: seeded with the critic, cut at episode ends, bootstrapped at truncation.**

```diff
<     running = 0.0
---
>     running = np.asarray(last_values, dtype=float)
...
<         running = rewards[t] + gamma * running
---
>         running = rewards[t] + gamma * running * (1.0 - dones[t])
```

plus the new [`add_truncation_bootstrap`](../../racer/algos/a2c.py#L113-L116). REINFORCE never
needed `dones` because each call saw one episode; here one car's column can hold the end of one
episode and the start of the next.

**Loss: advantage instead of return, plus the critic's regression.**

```diff
<     return -(logp * returns).mean()
---
>     advantage = returns - values
>     policy_loss = -(logp * advantage.detach()).mean()
>     value_loss = (values - returns).pow(2).mean()
>     return policy_loss + value_coef * value_loss - entropy_coef * entropy.mean(), value_loss
```

**Update: one more network, and a clip.**

```diff
<     optimizer = torch.optim.Adam(actor.parameters(), lr=cfg.lr)
---
>     critic = Critic(obs_dim(env_cfg), cfg.hidden)
>     params = list(actor.parameters()) + list(critic.parameters())
>     optimizer = torch.optim.Adam(params, lr=cfg.lr)
...
>         torch.nn.utils.clip_grad_norm_(params, cfg.max_grad_norm)
```

**Bookkeeping.** An episode can now start in one rollout and end in a later one, so the
training return can no longer be read off a batch: `car_return` and `car_len` accumulate each
car's current episode across rollouts and report it when it ends
([lines 204-213](../../racer/algos/a2c.py#L204-L213)). A rollout in which no episode ended logs
`nan` for `train_return_mean` and `episode_len_mean`; with 16 cars and 32 decisions that is
common once cars survive, which is why the console shows `return nan` so often. The two new
columns are `value_loss` and `explained_variance`.

## Why plain A2C does not settle

Some causes are visible in the logs and checkpoints; the cures are lesson 07's.

**One small, correlated batch per update.** Each update uses 512 decisions: 16 cars times 32
*consecutive* decisions. Consecutive decisions of one car are nearly the same state, so the batch
holds far less information than 512 independent samples. Then it takes a full Adam step with
`lr = 7e-4` and throws the batch away. 8,790 such steps add up to a lot of movement driven by
small samples. Nothing bounds how far one update moves the policy (PPO's clipped objective is
exactly such a bound).

**The critic is only moderately good.** Explained variance (median over all updates) is
0.33-0.39 on the oval and 0.43-0.48 on twisty: the critic removes about a third to a half of the
variance of the targets ([`eval_history.py`](scripts/eval_history.py) prints the quartiles). It
also breaks down exactly when the policy does. In seed 2's collapse, the value loss was 0.7-2.3
for iterations 8611-8711 and jumped to 15.2, 82.9, 43.8 at iterations 8721, 8731, 8751, with
explained variance falling to 0.19-0.21 (`metrics.csv`). The policy started crashing in new places,
the critic's predictions stopped matching, and its advantages, the actor's only learning signal,
became wrong right when they mattered most. Which came first cannot be read off these numbers;
the two feed each other.

**No advantage normalization.** The advantages are used at whatever scale the returns have,
and that scale grows as the car learns to collect more reward (returns near 150-230 per episode
later, against -14 at the start). Adam rescales gradients by their running size, which absorbs
slow changes, but a batch with unusually large advantages (one with crashes in it) still
produces an unusually large step. PPO normalizes advantages per batch.

**The gradient clip is always on, and the critic owns it.**
[`docs/lessons/scripts/a2c_grad_split.py`](scripts/a2c_grad_split.py) measures the two gradients
separately on 20 rollouts collected with a checkpoint (twisty seed 0):

```

  value_coef 0.25: |actor grad|  0.108, |critic grad|  0.117, total  0.178 (medians); clipped in   0% of rollouts, median scale 1.000
  value_coef  0.5: |actor grad|  0.108, |critic grad|  0.233, total  0.289 (medians); clipped in   5% of rollouts, median scale 1.000
  value_coef  1.0: |actor grad|  0.108, |critic grad|  0.467, total  0.498 (medians); clipped in  50% of rollouts, median scale 0.981

uv run python docs/lessons/scripts/a2c_grad_split.py runs/a2c-20261123-205730-s0 latest 0.25 0.5 1.0
  value_coef 0.25: |actor grad|  1.088, |critic grad|  1.291, total  1.947 (medians); clipped in 100% of rollouts, median scale 0.257
  value_coef  0.5: |actor grad|  1.088, |critic grad|  2.583, total  2.908 (medians); clipped in 100% of rollouts, median scale 0.172
  value_coef  1.0: |actor grad|  1.088, |critic grad|  5.165, total  5.336 (medians); clipped in 100% of rollouts, median scale 0.094
```

Early (iteration 500) the clip almost never acts. By the end every update is clipped, to about
a sixth of its length with the default `value_coef = 0.5`, and the critic's part is the larger
one. Clipping scales *both* networks' gradients by the same factor, so a batch where the critic is
badly wrong (a big critic gradient) also shrinks that batch's actor step. Adam's per-parameter
normalization absorbs a scale that stays constant, but this one changes from batch to batch.
Experiment 2 changes the weight.

## The unbounded mean

Lesson 05 pointed out that the actor's mean has no tanh: the network can ask for throttle 5, and
the simulator clips it to 1. [`docs/lessons/scripts/policy_means.py`](scripts/policy_means.py)
prints a checkpoint's *unclipped* means over the states of its evaluation episode and over
training-like states (16 cars sampling actions for 512 decisions). On the final checkpoints:

| run | start-line throttle mean | throttle mean > 1 (eval states / training-like states) | steer mean range on eval states |
|---|---|---|---|
| oval s0 | +4.10 | 6% / 12% | -8.12 .. +7.45 (48% outside [-1, 1]) |
| oval s1 | +4.28 | 7% / 18% | -1.42 .. +2.82 |
| oval s2 | +5.09 | 10% / 23% | -3.35 .. +6.41 |
| twisty s0 | +8.44 | 34% / 40% | -7.84 .. +5.62 (50% outside) |
| twisty s1 | +10.11 | 37% / 42% | -6.55 .. +5.32 |
| twisty s2 | +9.04 | 47% / 51% | -8.05 .. +6.60 |

and twisty seed 0's start-line throttle mean over training:

```
uv run python docs/lessons/scripts/policy_means.py runs/a2c-20261123-205730-s0 500 1000 2000 4000 6000 8000

iteration    500   1000   2000   4000   6000   8000
throttle   +0.26  +1.04  +3.39  +5.47  +8.06  +8.83      (std about 0.6 falling to 0.5)
```

The mean drifts steadily out of the range and never comes back. Why, and why it matters:

- **While samples still straddle the boundary, the gradient pushes outwards.** On the start line
  full throttle is right. With a mean of 1.2 and std 0.6, a third of the samples land below 1
  and give *less* throttle, which turns out worse: negative advantage, so the mean is pushed away
  from them, upwards. That continues until practically no sample falls below 1, two to three
  stds above it (a mean of 2.2-2.8 at std 0.6).
- **Beyond that, there is no signal at all.** If every sample from a state clips to the same
  action, the outcome does not depend on which sample was drawn, so the advantage is independent
  of the score `(a - μ)/σ²`, and `E[(a - μ)/σ² · A] = E[(a - μ)/σ²] · E[A] = 0`: the expected
  gradient from that state is zero, only noise is left. Nothing pulls the mean back, while
  updates for *other* states move the shared weights and drag this mean along, in any direction.
  Hence the random-looking ±8 steer means.
- **What it costs.** Exploration in those states is gone: the policy cannot discover that
  slightly less throttle would be better there until the mean has wandered all the way back to
  the boundary, which can take many updates. And the policy becomes bang-bang: a steer mean of +7
  and one of +1.2 drive identically, and when the mean finally crosses the boundary, the action
  changes abruptly. Lesson 05's experiment 2 showed the extreme case in REINFORCE: a throttle mean
  stuck at +1.15 to +2.64 everywhere, every episode a full-throttle crash, for the rest of the run.

The standard remedies (squash the mean with tanh, or sample in an unbounded space and squash
the action, correcting the log-probability) are not used here; the actor is shared with PPO, whose setup
lesson 07 matches against Stable-Baselines3, and this lesson's point is to see the problem.

## Experiments

Both experiments use twisty with a budget of **1,500,000 env steps** instead of 4.5M
(`--set env_steps_budget=1500000`), seeds 0 and 1, and compare against the defaults run with the
same budget (`runs/a2c-20261123-213731-s0`, `runs/a2c-20261123-213732-s1`; their first laps came at
the same iterations as the main runs', 510 and 620). Runs took 253-271 s, the `n_steps = 8` ones
356-364 s, six to eight sharing the machine, 2026-11-23. Two seeds are few: read the results as
"what can happen".

```sh
uv run racer train a2c --set env_steps_budget=1500000            # the defaults at this budget
uv run python docs/lessons/scripts/eval_history.py runs/a2c-<run> --short
uv run python docs/lessons/scripts/noisy_vs_mean_laps.py runs/a2c-<run>
```

### 1. Rollout length: `n_steps` 8 vs 32

**Change.** Each car drives 8 decisions per update instead of 32. An update now uses
`16 × 8 = 128` decisions, so the same budget buys four times as many updates (11,719 instead of
2,930), and every target looks at most 8 rewards ahead before handing over to the critic.
Evaluations stay 5,120 env steps apart (`eval_every = 40` instead of 10).

**Predict.** More updates sounds faster. But each one is noisier, and every target leans harder
on the critic: a crash 20 decisions ahead reaches today's target only through `V`. What will
explained variance do, and does a higher one mean a better critic?

**Run.**

```sh
uv run racer train a2c --set env_steps_budget=1500000 --set n_steps=8 --set eval_every=40
```

<details><summary>What we got</summary>

| `n_steps` | seed | run directory | updates | first lapping evaluation | evaluations that lapped | final evaluation | explained variance (median) | noisy final, laps 0/1/2 |
|---|---|---|---|---|---|---|---|---|
| 32 | 0 | `runs/a2c-20261123-213731-s0` | 2,930 | 261,120 steps | 58 of 293 | 2 laps, 40.98 s | 0.60 | 0/0/32 |
| 8 | 0 | `runs/a2c-20261123-213203-s0` | 11,719 | 1,121,280 steps | 17 of 293 | 0 laps, 298 m | **0.97** | 21/11/0 |
| 32 | 1 | `runs/a2c-20261123-213732-s1` | 2,930 | 317,440 steps | 100 of 293 | 2 laps, 41.33 s | 0.49 | 0/0/32 |
| 8 | 1 | `runs/a2c-20261123-213207-s1` | 11,719 | 1,146,880 steps | 53 of 293 | 0 laps, 375 m | **0.86** | 31/1/0 |

- **Eight-step rollouts were much slower to learn** on both seeds: first lap after about 1.1M
  steps instead of 0.26-0.32M, both final evaluations crash, and the final noisy policies finish
  no episode with two laps. Four times the updates did not help; each saw a quarter of the data,
  through a critic that had to carry more of the target.
- **Explained variance went *up*, to 0.86-0.97.** That is not a better critic. With 8-step
  rollouts a target holds between 1 and 8 real rewards (4.5 on average) plus `γ^k V(s_{t+k})`, the critic's own
  prediction a few decisions later, which is nearly `V(s_t)` again. A critic predicting targets
  made mostly of itself scores well by construction. Explained variance measures agreement with
  the targets, not with the true returns; compare it only between runs with the same `n_steps`.
- The flip side of the bias-variance trade: the 32-step targets contain more real rewards, so
  their errors are noisier but less dependent on what the critic currently believes. In these
  runs that was the better side.

</details>

### 2. Critic weight: `value_coef` 0.25 vs 0.5 vs 1.0

**Change.** The weight of the critic's squared error in the summed loss. Actor and critic have
no shared weights, so it would only rescale the critic's gradient, which Adam mostly undoes, were
it not for the shared gradient clip measured above: the larger `value_coef`, the larger the
critic's part of the norm and the more both gradients get scaled down.

**Predict.** With 1.0 the clip shrinks every update more (median scale 0.094 at the end of the
main run instead of 0.172); with 0.25, less (0.257). Faster or slower learning? Does the critic's
fit change?

**Run.**

```sh
uv run racer train a2c --set env_steps_budget=1500000 --set value_coef=0.25
uv run racer train a2c --set env_steps_budget=1500000 --set value_coef=1.0
```

<details><summary>What we got</summary>

| `value_coef` | seed | run directory | first lapping evaluation | evaluations that lapped | final evaluation | fastest lap | explained variance (median) |
|---|---|---|---|---|---|---|---|
| 0.25 | 0 | `runs/a2c-20261123-213205-s0` | 947,200 steps | 55 of 293 | 2 laps, 42.83 s | 40.37 s | 0.55 |
| 0.5 | 0 | `runs/a2c-20261123-213731-s0` | 261,120 steps | 58 of 293 | 2 laps, 40.98 s | 40.15 s | 0.60 |
| 1.0 | 0 | `runs/a2c-20261123-213206-s0` | 629,760 steps | 108 of 293 | 2 laps, 41.52 s | 39.87 s | 0.46 |
| 0.25 | 1 | `runs/a2c-20261123-213208-s1` | 552,960 steps | 91 of 293 | 2 laps, 41.63 s | 40.18 s | 0.42 |
| 0.5 | 1 | `runs/a2c-20261123-213732-s1` | 317,440 steps | 100 of 293 | 2 laps, 41.33 s | 39.27 s | 0.49 |
| 1.0 | 1 | `runs/a2c-20261123-213210-s1` | 604,160 steps | 85 of 293 | 0 laps, 523 m | 39.53 s | 0.51 |

- **No setting is clearly better.** All six runs lapped twisty within the 1.5M steps, the fastest
  laps span only 39.3-40.4 s, and five of six final evaluations drove both laps. The default 0.5
  had the earliest first lap on both seeds, but with evaluations this unsteady (each run lapped in
  only 55-108 of 293) a single first-lap number is a weak signal.
- **Explained variance barely moved** (0.42-0.60, with no order by `value_coef`). Weighting the
  critic's loss more did not make it fit better, consistent with Adam absorbing most of the
  scale: what `value_coef` changes here is mostly the clip's scale factor, and that acts on both
  networks at once.
- One 1.0 run ended in a crashing evaluation (seed 1, 523 m): more of the instability described
  above, not something two seeds can pin on the setting.

</details>
